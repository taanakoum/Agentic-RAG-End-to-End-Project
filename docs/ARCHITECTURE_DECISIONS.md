# Architecture Decisions

Format: ID, date, context, options considered, decision, consequences. Required topics (record when decided): LangGraph checkpoint persistence; same-thread concurrency mechanism; outbox + dispatcher design; Celery/asyncio execution model; Qdrant collection layout + sparse method + point ID scheme; PDF/object storage; memory storage; streaming validation; job recovery/reconciliation; deletion consistency; Streamlit auth session handling; free-hosting choices.

## ADR-001 (2026-11-08): Target Python 3.13, managed by uv
- Context: default interpreter is 3.14.3; uv has 3.13.12 installed. Planned deps include torch, pymupdf, sentence-transformers, which lag on newest Python versions.
- Options: 3.14, 3.13, 3.12.
- Decision (provisional): 3.13 via `.python-version` + uv lockfile. To be confirmed in Phase 1 by an actual `uv sync` of the full dependency set; if resolution fails, fall back to 3.12 and amend this ADR.
- Consequences: the Docker base image must use the same minor version.

## ADR-002 (2026-11-08): Repo root is the project folder
- Decision: spec layout is rooted directly here (`backend/`, `frontend/`, `docs/` ...) instead of a nested `agentic-rag-platform/` folder, since the folder already holds CLAUDE.md and docs.

## ADR-001 update (2026-11-08)
`uv sync` of the Phase 1 dependency set resolved and all tests ran on Python 3.13.12. Heavy ML dependencies (torch, sentence-transformers, langgraph) are not yet in the lock; revisit if resolution fails when they are added.

## ADR-003 (2026-11-08): Celery/asyncio execution model
- Context: spec requires one explicit model, no ad-hoc `asyncio.run()`.
- Decision: Celery tasks are plain synchronous functions using synchronous clients (SQLAlchemy sync engine over psycopg, redis-py, qdrant-client). The API uses the async stack (asyncpg, redis.asyncio, AsyncQdrantClient). Alembic uses the sync psycopg engine.
- Consequences: two DB drivers (asyncpg for the API, psycopg for workers/migrations; psycopg is also needed later for the LangGraph Postgres checkpointer). Celery config: acks_late, reject_on_worker_lost, prefetch 1, visibility_timeout = hard time limit + 300 s. On Windows dev, workers must use `--pool=solo` (prefork is unsupported); Docker/Linux uses prefork.

## ADR-004 (2026-11-08): Object storage keys and adapter
- Decision: synchronous `ObjectStorage` protocol. Keys are application-generated '/'-separated segments matching `[A-Za-z0-9_][A-Za-z0-9._-]{0,127}`; never derived from user filenames. Local adapter writes via temp file + fsync + `os.replace` (atomic), computes SHA-256 and size while streaming, enforces `max_bytes`, and verifies the resolved path stays inside the root. The S3-compatible adapter is deferred (KI-007).

## ADR-005 (2026-11-08): Health endpoints
- `/health/live` (no dependencies), `/health/ready` (PostgreSQL, Redis, Qdrant, storage; 503 on failure), `/health/workers` (Celery control ping; 503 if none). Unauthenticated; responses carry only ok/error per component, details go to logs. Worker ping uses a fresh broker connection per probe because a pooled connection went stale after a Redis restart (found in manual failure testing, see EXECUTION_LOG Entry 4).

## ADR-006 (2026-11-08): Proceed to Phase 2 while G1 is blocked
- Context: G1 needs Docker (KI-003). Phase 1 backend components are verified on native services; only the Docker artifacts are unverified.
- Decision: continue with Phase 2 (its gate G2 needs only PostgreSQL/Redis, available natively). Phase 1 stays "TESTED (native), G1 BLOCKED" until Docker verifies it. Docker-dependent work is never marked VERIFIED.

## ADR-007 (2026-11-08): Access/refresh token design
- Decision: short-lived HS256 JWT access tokens (15 min) bound to a session id (`sid` = refresh-token family) + opaque rotating refresh tokens stored hashed in PostgreSQL. Each authenticated request verifies in PostgreSQL that the user is active and the session has a live refresh token.
- Options rejected: pure stateless JWT (no immediate logout/revocation); Redis-only session store (Redis must never be the only copy of critical data).
- Consequences: one small indexed query per authenticated request in exchange for immediate revocation; reuse of a rotated refresh token revokes the family; concurrent refresh of one token yields exactly one success. HS256 with a single secret: no key rotation yet (documented in SECURITY.md).

## ADR-008 (2026-11-08): Rate limiting fails closed
- Decision: Redis fixed-window counters; on Redis failure auth endpoints return 503 rather than skipping limits. Per-account lockout counts failures only and is keyed on the submitted identity (existing or not) to avoid account enumeration.
- Consequences: a Redis outage disables login/registration (security over availability). Fixed-window boundary bursts and deliberate victim lockouts are accepted limitations (SECURITY.md).

## ADR-009 (2026-11-08): Error handling and middleware
- Decision: one `AppError` hierarchy rendered by central handlers into a single JSON contract; validation errors omit submitted values; pure ASGI middlewares for request IDs and body-size limits (no BaseHTTPMiddleware, so SSE streaming stays safe). The body-size middleware answers 413 itself and signals disconnect to the app, because FastAPI converts exceptions raised from `receive()` into 400.

## ADR-010 (2026-11-08): One-time tokens, email delivery, MFA, key rotation
- One-time tokens (password reset 1 h, email verification 24 h): 384-bit random, only SHA-256 stored in `one_time_tokens`, consumed with a single atomic `UPDATE ... WHERE used_at IS NULL AND expires_at > now RETURNING` (concurrent use of one token succeeds exactly once). A new request invalidates older unused tokens of the same purpose. A weak new password rolls back the consume so the token stays usable.
- `forgot` always returns 202 and does the lookup + email in a background task; rate limits (per IP and per submitted email, existing or not) are applied in-request so the response never depends on the account.
- Password reset signs out every session; password change signs out every other session. Both send a best-effort notification email.
- Email goes through an `EmailSender` protocol: `file` backend (writes .eml; dev/test only, prod config forbids it) and `smtp` (stdlib smtplib in a thread, STARTTLS/SSL). The SMTP adapter is tested against a real aiosmtpd server.
- MFA: RFC 6238 TOTP via pyotp (30 s step, +/-1 step window), secret stored Fernet-encrypted (`MFA_ENCRYPTION_KEY`), replay protection by atomically advancing `last_used_step`, 10 single-use recovery codes stored as SHA-256, attempts rate limited per user (5 / 5 min). Login returns `mfa_required` + a 5-minute `mfa` JWT (different `type`, no `sid`) that only `/auth/mfa/verify` accepts.
- JWT key rotation: tokens carry `kid`; `JWT_KEY_ID`/`JWT_SECRET` sign, `JWT_RETIRED_KEYS` (JSON kid->secret) only verify. Unknown kid is rejected; a token without kid verifies only against the active key. Procedure: set new active key, move the old one to retired, remove it after `ACCESS_TOKEN_TTL_S`.

## ADR-011 (2026-11-08): S3 adapter
- boto3 (sync, matching the sync `ObjectStorage` protocol), `upload_fileobj` for streaming/multipart with a counting+hashing reader (enforces `max_bytes`, aborts multipart on failure), `open()` returns a seekable spooled temp copy (PDF parsers need seek), `delete_prefix` paginates + batch deletes, optional key prefix to share a bucket between environments. Selected with `STORAGE_BACKEND=s3`. HEAD cannot distinguish a missing bucket from a missing key, so `exists()` returns False there; reads/writes/deletes and the readiness probe fail loudly.

## ADR-012 (2026-11-08): Qdrant layout, point ids, payload
- One collection `<prefix>chunks`; named vectors `dense` (cosine, size `EMBEDDING_DIM`, default 384) and `sparse` (IDF-modified BM25 term weights from fastembed `Qdrant/bm25`). Keyword payload indexes on `user_id` (marked tenant index) and `document_id`.
- Point id = `uuid5(NAMESPACE, "<document_id>:<version>:<chunk_index>")`: re-running a job overwrites the same points, so duplicate delivery, retries and "Qdrant OK but DB update failed" cannot create duplicates. After a successful index of version N the worker deletes the document's points of other versions.
- Payload: user_id, document_id, document_version, chunk_id (= point id), chunk_index, filename, page_number, heading, ingestion_timestamp, embedding_model_version, text. Chunk text lives in the payload (Qdrant is a derived index, rebuildable from object storage + PostgreSQL by re-indexing) so citation excerpts can be verified against stored text later.
- Every maintenance filter (delete/count) includes BOTH user_id and document_id. Query-time filters arrive in Phase 4.
- Embedder is a small protocol (`embed_dense`, `embed_sparse`). Production: FastEmbed (BAAI/bge-small-en-v1.5 as the quantized ONNX build, plus bm25), run locally. Tests use a deterministic hash embedder defined only under `backend/tests/`; two tests use the real models.

## ADR-013 (2026-11-08): OCR for scanned PDFs: RapidOCR (open source), not Tesseract
- Requirement: OCR fallback in the background worker only, bounded, status recorded. Tesseract is not installed here and needs a system install.
- Chosen: pypdfium2 (render page, BSD/Apache) + RapidOCR (PP-OCR ONNX models bundled inside the wheel, Apache-2.0) on onnxruntime CPU. No download, no system package, same behaviour natively and in Docker. Measured on the dev laptop: model load 2.7 s, then ~1.1 s per page at 200 DPI; the generated test page ("INVOICE NUMBER 48213 / TOTAL AMOUNT DUE 1250 DOLLARS / ...") was read back exactly.
- Docling was considered (open source, layout + table aware, uses RapidOCR internally on some platforms) and NOT adopted for now: it pulls PyTorch and layout models for features (table structure, reading order) that the spec does not require yet, and it would be a much heavier worker image. The parser/OCR code sits behind small interfaces (`OcrEngine`, `extract_*`), so Docling can be added later if evaluation shows chunk quality gains.
- Limits: `OCR_ENABLED`, `OCR_MAX_PAGES` (40), `OCR_DPI` (200), `MIN_TEXT_CHARS_PER_PAGE` (25 alphanumerics below which a page is OCRed). Result recorded on the document: `ocr_status` (not_needed/used/limited/failed/disabled) and `ocr_pages`. Pages that stay empty are never chunked; a document with no meaningful text fails permanently with `DOCUMENT_NO_TEXT` and an explanation.
- Known limit: the bundled PP-OCR models target English/Chinese text; other scripts need other recognition models (not configured).

## ADR-014 (2026-11-08): Outbox, reconciliation, retries, deletion
- Upload commits document + ingestion_job + outbox_event in ONE transaction (insert-or-fetch on the partial unique index `(user_id, content_hash) WHERE deleted_at IS NULL` decides concurrent identical uploads; the loser deletes its own stored copy).
- Dispatcher: `SELECT ... FOR UPDATE SKIP LOCKED`, `send_task`, mark sent (at-least-once). Runs (a) right after upload in the API (best effort, low latency), (b) every `OUTBOX_DISPATCH_INTERVAL_S` from Celery Beat. A broker outage leaves rows unsent with an error recorded.
- Tasks: job claimed by compare-and-set `queued -> processing` (duplicate deliveries skip); every document stage change is a compare-and-set on status; `acks_late` + `reject_on_worker_lost`; transient failures release job/document to queued and retry with exponential backoff + jitter up to `INGESTION_MAX_ATTEMPTS`, then FAILED (recoverable, retry via API); permanent failures (corrupt, encrypted, no text, integrity, ownership) FAIL immediately (not recoverable). Workers verify document ownership and the stored file's SHA-256 before processing.
- Reconciler (Beat, every `RECONCILE_INTERVAL_S`): republish queued jobs whose message vanished (at most once per TTL), recover jobs stuck in processing (worker died) or fail them after max attempts, republish unfinished purges, prune sent outbox rows older than 7 days.
- Deletion: `DELETE` tombstones the row (`deleted_at`, instantly invisible to the API) and writes a purge outbox event in the same transaction; the purge task removes Qdrant points (user_id + document_id filter), the storage prefix, then hard-deletes the row LAST, so any failure is retried by the task and, if lost, by the reconciler. A purge waits while a job for the document is processing; a worker that finishes after a delete removes the vectors it wrote.
- State table deviation: PENDING and VALIDATING exist in the state machine, but because validation is synchronous in the API a new document is inserted directly as QUEUED.

## ADR-015 (2026-11-08): Docling is the default PDF pipeline; OCR only when a page needs it (supersedes ADR-013's "Docling not adopted")
- Pipelines (`PDF_PIPELINE`): `docling` (default), `light` (pypdf + RapidOCR, cheap fallback), `structured` (TXT/MD/CSV/DOCX).
- Docling converts with layout and table understanding; OCR is switched on only if at least one page has no usable text layer. Text PDFs and all non-PDF formats never touch OCR.
- Chunking uses Docling's `HybridChunker` (320 tokens, heading context prepended for embedding). Pages Docling recognised but did not chunk (e.g. a scanned page it labelled a heading) fall back to the light chunker, so no page is silently dropped.
- Evidence: `evaluation/reports/chunking_eval.md` (6 strategies, 36 questions, real embedding models). Docling HybridChunker: hybrid hit@3 0.81, MRR 0.70, versus fixed 1000-char chunks 0.56 / 0.55. Docling markdown + LangChain header splitter scored slightly higher on this corpus (hit@3 0.86, MRR 0.72) but depends on a markdown export; the HybridChunker was kept because it is token-aware, keeps tables intact and keeps page numbers per chunk, which citations need. The corpus is synthetic and small (KI-018).
- LangChain splitters were evaluated, not adopted as a pipeline dependency. Cost: about 1.7 s/page CPU for conversion (KI-021).

## ADR-016 (2026-11-08): Sandboxed parsing with warm process pools
- Untrusted files are parsed only in child processes: wall-clock timeout, memory cap (Windows Job Object; POSIX `RLIMIT_DATA`), no process spawning (Windows), scrubbed environment (no secrets), JSON-lines protocol.
- The child runs the base interpreter with the venv's site-packages on `PYTHONPATH` (the venv launcher is itself a process and is blocked by the job's active-process limit).
- `PersistentSandbox` keeps a warm child (models loaded once), recycles it after `max_jobs`, and kills it on timeout or crash; `SandboxPool` serves concurrent callers. Inspection (cheap) and parsing (heavy) use separate pools; one-shot mode exists for tests.
- Trade-off: a warm child is reused across documents of different users, so it is recycled periodically and keeps no per-user state; one child per document would be stricter but slower.

## ADR-017 (2026-11-08): Chunking method
- Sentence- and section-aware packing with a token budget; headings detected per line and tracked as a section path; chunks may span page breaks and record `page_number`..`page_end`; headers/footers removed, hyphenation repaired, hard-wrapped lines unwrapped before chunking.
- Embedding text = `title > section path` + body (contextual header); the stored and cited text is the unmodified body.
- CSV is chunked as row groups that repeat the header row; Markdown by heading; DOCX by heading styles and tables.

## ADR-018 (2026-11-08): Multiple formats, validated by content
- `FORMATS` maps extension to (format, allowed MIME types, stored MIME); the declared extension/MIME is only a hint. PDF: magic bytes + parser. DOCX: zip structure, entry count/size/ratio limits, XML parsed without entities. TXT/MD/CSV: size limit, binary rejection, encoding detection, row/column caps. Same state machine, outbox and indexing as PDFs; `documents.source_format` and `documents.parser` are recorded (migrations 0005, 0007).

## ADR-019 (2026-11-08): Account deletion, breached passwords, verified-email gating
- Deletion: `DELETE /auth/account` with password (and MFA code when enabled). One transaction revokes sessions, deactivates and tombstones the user, tombstones every document with purge events and queues a `purge_user` event. The worker purges vectors, files and finally the user row (email freed). Idempotent; the reconciler requeues unfinished purges.
- Breached passwords: offline check against about 135k SecLists passwords (MIT) plus a "core" reduction (trailing digits/symbols, leet). No external service. Limit: not a full breach corpus.
- Verified-email gating: `REQUIRE_VERIFIED_EMAIL` guards document and ingestion routes with the `VerifiedUser` dependency (403 `EMAIL_NOT_VERIFIED`); auth/account routes stay available so users can verify. Production config validation requires it to be true.

## ADR-020 (2026-11-08): Orphan sweep
- Beat task `sweep-orphans` lists storage (`iter_objects`, with modification times), deletes objects in the generated key layout that have no document row and are older than `ORPHAN_GRACE_S`, and clears stale temporary uploads. The grace period prevents racing an upload that has written the object but not yet committed its row.

## ADR-021 (2026-11-08): Concurrency model
- Blocking work never runs on the event loop: Argon2 in threads behind a semaphore; hashing/validation on a dedicated executor; parsing in sandbox processes; a larger default thread pool; single-query hot paths (windowed list query, `get_owned_with_job`); notification emails as background tasks; uvicorn `--workers` for multiple cores.
- Guardrail test measures event-loop lag during a mixed burst of 12 users with production-strength Argon2 and fails if blocking calls appear (confirmed to fail against a mutant that hashes on the loop).
- Benchmark (`load_testing/concurrency_bench.py`, dev laptop, local services, one client process): throughput rose from 87 to 259 req/s with 3 API processes, and upload p50 fell from 1813 ms to 227 ms after the optimisations. Dev-machine numbers only (KI-022), not capacity claims.

## ADR-022 (2026-11-08): Hybrid retrieval, fusion, reranking and authorization (Phase 4)
Evidence: `evaluation/reports/retrieval_eval.md|json`, `retrieval_inspection.md` (reproduce with `evaluation/retrieval/run_eval.py`). Dataset `retrieval-synth-v1`: 6 synthetic documents, 43 pages, 72 production (Docling) chunks, 36 natural questions plus 36 auto-derived heading-keyword queries; relevant = chunk containing the answer sentence. Answer sentences omit the topic words (only the section heading has them) and every document has distractor sections, so this is not a lexical-overlap give-away, but it IS small and synthetic: one question is 2.8 points, and the numbers rank configurations on this data only. CPU only (Intel Family 6 Model 140 laptop CPU, Windows), models cached.

**Structure.** `app/retrieval/`: `retriever.py` (authorized search), `fusion.py` (RRF), `rerank.py` (cross-encoder protocol), `warmup.py`; `services/retrieval_service.py` adds PostgreSQL authorization; `POST /api/v1/search`.
**Sparse:** BM25 via Qdrant sparse vectors (FastEmbed `Qdrant/bm25`, IDF-modified in Qdrant, query side = unique stemmed tokens, weight 1). Chosen over SPLADE: no extra model or GPU, deterministic, indexed at ingestion (ADR-012); SPLADE would add a transformer pass per chunk and per query.
**Fusion:** RRF done in application code over two separately filtered Qdrant queries (so each ranker's rank/score is observable and the result can state which ranker found each chunk), `k = 60`, deterministic tie-break. Server-side `Fusion.RRF` was not used because it hides per-ranker ranks and cannot degrade a single failing leg. k = 10 vs 60 made no meaningful difference (natural MRR 0.81 vs 0.82); 60 kept.
**Results (natural questions, hit@1 / hit@3 / MRR / NDCG@5; median latency incl. query embedding):**
| configuration | hit@1 | hit@3 | MRR | NDCG@5 | median ms |
|---|---|---|---|---|---|
| dense (bge-small) | 0.58 | 0.72 | 0.69 | 0.72 | 9 |
| sparse (BM25) | 0.53 | 0.81 | 0.66 | 0.71 | 3 |
| hybrid RRF k=60 | 0.72 | 0.92 | 0.82 | 0.85 | 10 |
| hybrid + MiniLM-L6 rerank (30 cand.) | 0.42 | 0.83 | 0.63 | 0.69 | 1500 |
| hybrid + bge-reranker-v2-m3 int8, 5 cand. (DEFAULT) | 0.94 | 0.94 | 0.94 | 0.94 | 2170 |
| hybrid + bge-reranker-v2-m3 int8, 10 cand. | 0.94 | 0.94 | 0.94 | 0.94 | 4327 |
| hybrid + bge-reranker-v2-m3 int8, 30 cand. | 0.97 | 1.00 | 0.99 | 0.99 | 14378 |
Heading-keyword queries (auto-derived, easier): dense 0.86 hit@1, BM25 0.14 (the heading words also occur in every chunk of the section, so BM25 cannot pick the right one), hybrid 0.78, default reranker 0.89.
**Findings.** (1) Hybrid beats either ranker alone on every natural-question metric (hit@3 0.92 vs 0.72 / 0.81), confirming both candidate sets are needed (unit and integration tests prove both rankers' candidates reach the fused set). (2) Reranking is NOT automatically good: the smaller ms-marco cross-encoders made ranking WORSE than no reranking (MiniLM-L6 hit@1 0.72 -> 0.42; L12 0.81; jina turbo 0.69) on this corpus, where the answer is one sentence inside ~300 tokens of filler. Only `BAAI/bge-reranker-v2-m3` (Apache-2.0, int8 ONNX, 0.57 GB) helped (hit@1 0.72 -> 0.94-0.97). (3) That model is expensive on CPU: ~0.45 s per candidate, so candidates are limited. 5 candidates (2.2 s median) reach hit@1 0.94; the remaining misses (2 of 36, e.g. q19 "How often are admin permissions reviewed?") are chunks that neither ranker places in their top candidates, i.e. a recall limit rather than a ranking one; 30 candidates recover them at 14 s. (4) The BGE query instruction made dense retrieval slightly worse here (hit@1 0.58 -> 0.50), so `DENSE_QUERY_PREFIX` stays empty.
**Decision.** Default pipeline = hybrid (40 + 40 candidates, RRF k=60) then rerank the top `RERANK_CANDIDATES=5` with `BAAI/bge-reranker-v2-m3-int8`; the remaining fused candidates follow in fused order so `top_k` is still filled. `RERANK_ENABLED=false` gives plain hybrid (10 ms). Reranking runs on a dedicated thread pool (`INFERENCE_THREADS`, default 2) with a timeout; on timeout/failure the fused order is returned and the response says `degraded: ["rerank_timeout" | "rerank_unavailable"]`. A failing dense or sparse leg degrades to the other; both failing is a 503. Models are loaded in the background at API start (`WARM_MODELS_ON_STARTUP`, enabled in compose) because the first use downloads them.
**Manual inspection** (retrieval_inspection.md, 14 queries): where dense and sparse disagreed, RRF almost always put the relevant chunk first (e.g. q06 dense rank 4, sparse 1 -> hybrid 1); the reranker moved the relevant chunk from rank 2 to 1 for q04, q08, q11; q19 is missed by every configuration within the candidate depth.
**Authorization (spec 04).** PostgreSQL first (owned, `completed`, not deleted; optional `document_ids`), then `user_id` + allowed `document_id` set in the filter of EVERY dense and sparse query, payload `user_id` re-checked, then a final PostgreSQL re-validation (deleted / re-indexed / no longer completed hits dropped). Each layer has a test that fails when the layer is removed (mutation-checked). Result chunks carry the citation fields (`chunk_id`, `document_id`, `document_name`, `page_number`, `page_end`, `section_path`, `text`) and `RetrievalResult.evidence_chunk_ids` is the evidence set that Phase 6 citation verification will check against.
**Not done / limits.** Query rewriting/expansion, MMR, parent-child and contextual compression were not added (no evidence they would help; spec says only if evaluation shows benefit). Evaluation is synthetic and tiny (KI-018 stays partly open); the reranker's CPU cost limits concurrency (KI-023); the Qdrant filter lists readable document ids (KI-024).

## ADR-023 (2026-11-08): Sessions, chat turns, same-thread concurrency, idempotency
Spec 05 asks us to choose and document a same-thread concurrency policy. Chosen (all enforced in PostgreSQL, tested with concurrent sessions and mutation checks):
- **Identifier mapping:** `user_id -> conversations.id (API session_id) -> conversations.thread_id (LangGraph thread, never shown to clients) -> chat_executions.id (execution_id, one per accepted chat request) -> messages.id`. Ownership is enforced at every access (`user_id` in every query; foreign, deleted and unknown ids are indistinguishable 404s).
- **Serialisation:** a row lock on the conversation (`SELECT ... FOR UPDATE`, re-read with `populate_existing`) serialises everything that appends to it. `conversations.last_seq` is the per-conversation counter, so message sequence numbers are gapless and ordered; `UNIQUE (conversation_id, seq)` is the safety net. Different conversations, even of one user, never contend.
- **One active execution:** partial unique index on `chat_executions(conversation_id) WHERE status='running'`. A second message while one is being answered is REJECTED with `409 CONCURRENCY_CONFLICT` (not queued, so a slow generation cannot pile up hidden work; the client retries or waits for the stream).
- **Leases:** every execution holds a lease (`CHAT_LEASE_S`, default 120 s, renewable). A request that arrives after a dead worker's lease expired marks that execution `failed/LEASE_EXPIRED` and proceeds; a late `complete()` from the dead worker is refused because the status is no longer `running`, so an answer or checkpoint can never be overwritten by a stale writer.
- **Idempotency:** the client's key is unique per conversation. Replaying a key returns the original execution (and the stored answer once completed) without creating messages; the same key with a different body is `409 IDEMPOTENCY_KEY_REUSED`; ten simultaneous retries create exactly one execution. A failed turn needs a new key to retry.
- **Completion is atomic:** the assistant message, the execution status and the conversation timestamp commit in one transaction. If generation succeeds but persistence fails, the response is NOT considered complete (the execution stays `running` until its lease lapses, then `failed`), and the user message is kept; Phase 6 will return an error event and never present an unsaved answer as saved.
- **Deletion during generation:** `DELETE /sessions/{id}` tombstones the conversation, cancels the running execution (`CONVERSATION_DELETED`) and queues a purge in the same transaction; the late `complete()` is refused. The worker then deletes checkpoints and the row (messages and executions cascade); a reconciler step republishes lost purges. Late checkpoint writes of a cancelled run are removed by the `sweep-checkpoints` beat task.
- A race found by the tests and fixed: the execution row was read before the conversation lock was taken, so six simultaneous completions all saw `running`; the locked re-read now uses `populate_existing`.
- Tests: `test_chat_turns.py` (30), `test_sessions_api.py` (20), `test_chat_lifecycle.py` (6); 14 mutants caught.

## ADR-024 (2026-11-08): LangGraph checkpointer = AsyncPostgresSaver (langgraph-checkpoint-postgres 3.2.0)
- One `AsyncConnectionPool` per process feeds `AsyncPostgresSaver`; opened lazily; `setup()` (library-versioned, idempotent) runs under a PostgreSQL advisory lock so several API workers starting together cannot race. State lives in PostgreSQL only (never in memory), so conversations survive a restart of every container (tested with a brand-new Infrastructure and pool).
- Windows: psycopg's async mode needs the selector event loop; the server gets it from `--loop app.chat.checkpointer:selector_event_loop` and the test suite from pytest-asyncio's loop-factory hook (the policy-based `use_selector_loop()` of this ADR was removed on 2026-11-13, see ADR-035 and KI-027); Linux containers are unaffected.
- Deletion: checkpoint rows (`checkpoints`, `checkpoint_blobs`, `checkpoint_writes`) are deleted with SQL in the same transaction as the conversation row; a contract test checks that the library's own `aget_tuple` no longer sees the thread, so a library schema change is caught.
- Not used yet: the checkpointer carries no real agent graph until Phase 6; the tests use a small LLM-free graph (2 nodes, reducers) to prove persistence, thread isolation, 25 concurrent threads and restart continuation.

## ADR-025 (2026-11-08): Long-term memory
- **Separate from chat history.** Tables `memories` (kind semantic|episodic|summary, importance 1-5, source user|consolidation, tombstone `deleted_at`, `index_state`) and `user_preferences` (memory OFF by default; retention days, default 365). PostgreSQL is the source of truth; Qdrant holds one derived dense vector per memory (collection `memories`, point id = memory id, `user_id` tenant index). Decision: PG + Qdrant (the suggested option), maintained by the worker via the transactional outbox (index, purge, reset), reconciled when messages are lost.
- **Retrieval by relevance only:** query embedding -> Qdrant search filtered by `user_id` with a score threshold (`MEMORY_MIN_SCORE`) and top-k (`MEMORY_SEARCH_K`) -> PostgreSQL re-check (deleted / foreign memories dropped even while their vector exists). The agent path returns nothing unless the user turned memory on; `last_used_at` is updated only for what was retrieved (does not count as an edit).
- **Consent and retention:** consolidation runs only for users with memory enabled; messages written while it was off are never examined later ("not retroactive"); the beat task `memory-retention` tombstones memories not updated or used within the owner's retention window.
- **Controlled consolidation (Celery):** after `MEMORY_CONSOLIDATE_EVERY` new messages (default 6) one idempotent task per conversation (row-locked, `memory_seq` watermark, duplicate deliveries and concurrent runs create nothing twice) runs a `MemoryExtractor`. The default `RuleExtractor` stores only explicit self-statements ("remember that...", "my name is...", "I prefer...", "I work at...") and ignores questions and assistant text. LLM-based episodic memories and conversation summaries need the agent phase's model provider (KI-026).
- **No sensitive data by default:** a heuristic filter (credentials/tokens/keys, payment cards with Luhn check, IBAN, SSN, emails, phone numbers, credentials in URLs) rejects manual memories (422 `sensitive_content`, the text is not echoed) and silently skips consolidation candidates. Conservative by design (a long digit group is refused even when the card checksum fails).
- **User control:** list/create/edit/delete/reset/search endpoints, preferences endpoint, per-user write rate limit, per-user cap, duplicate detection (case/space-insensitive), delete = tombstone now + vector and row removed by the worker; reset requires `{"confirm": true}`. Account deletion removes rows and vectors; deleting a conversation keeps the memories learned from it (`source_conversation_id` becomes NULL).
- Tests: 27 unit, 33 API, 13 pipeline integration tests (real worker, PostgreSQL, Qdrant); mutation-checked.

## ADR-026 (2026-11-11): Single-agent RAG (LangGraph), structured output, citation verification, chat turns
Planned with an Opus 5.5 pass (CLAUDE.md "Model escalation"); executed and verified by Sonnet. Where the plan and the code differ, the code is described here.
- **Graph** (`app/agents/single.py`, `StateGraph(AgentState, context_schema=TurnContext)`): `classify` -> `respond_smalltalk` | `respond_clarify` | `prepare_query` -> `retrieve` -> (`respond_insufficient` | `generate` -> `check_output` -> `finalize` | repair `generate` | `respond_fallback`) -> `finalize` -> `persist`. Every branch ends in `finalize`, which validates the user-facing `RAGResponse`. The only loop is the bounded repair edge (`LLM_REPAIR_ATTEMPTS`, default 1, max 2) plus `recursion_limit=25` as a backstop. Spec nodes map as: input validation = ChatTurnService + classify; retrieval-necessity = classify (deterministic); rewrite = `prepare_query`; hybrid retrieval + rerank + context construction + evidence analysis = `retrieve` / `evidence_gate` / `build_answer_messages`; grounded generation = `generate`; citation verification + Pydantic validation = `check_output`; persistence = `persist`.
- **Routing without a model** (`routing.py`): smalltalk is a FULL match on an allowlist ("hi, my SSN is ..." is not smalltalk) and is answered from fixed text (no model call, no quota); messages without any content word ("???", "what is it?") get a clarification; everything else searches the user's documents. Deviation from the plan: a single keyword ("revenue") is a legitimate lookup, so only zero content tokens trigger clarification. A query-rewrite model call happens only for a short follow-up that leans on history (anaphora markers, <= 12 tokens) and degrades to "previous question + follow-up" if the provider fails.
- **Structured output** (`schemas.py`, `llm/structured.py`): the model returns a `DraftAnswer` (extra=forbid): answer with `[S1]` markers, `citations [{source, quote, page?}]`, `insufficient_evidence`, `clarification_needed`, `follow_up_questions`, `support supported|inference|not_found`. The schema and an example are always in the system prompt (works in every `LLM_JSON_MODE`; `response_format` is added on top where the provider supports it and downgraded on a 400). The parser tolerates fences and surrounding prose but never "repairs by guessing"; error hints sent back for the one repair call are field paths and error kinds only, never values.
- **Server-side citation verification** (`citations.py`): per citation the label must be one shown for THIS execution (the authorized evidence set), the chunk id must equal `point_id(document, version, chunk_index)`, PostgreSQL must still say the document is the user's, completed and at the retrieved version, a claimed page must lie in the stored page range, and the quote must occur in the stored text. `document_name`, `page_number`, `chunk_id` and `document_id` come from stored data; the excerpt is the stored sentence, not the model's words. Invalid citations are dropped; a factual answer left without a valid citation is repaired once, then replaced by a server-written "cannot back this with citations" answer. Markers are renumbered `[1]`, `[2]` in order of appearance. `RetrievalResult.readable_documents` lets the agent tell "no documents yet" from "nothing relevant".
- **Prompt-injection hygiene** (`context.py`): the system message is constants only; sources and memories are data inside `<source-NONCE ...>` / `<memory-NONCE>` blocks, the model sees labels S1..Sk only (never chunk or document ids), tag-like text and attacker-controlled filenames are neutralised, the context is budgeted. Deviation from the plan: the nonce is HMAC-derived (keyed with a server secret over user, question and chunk ids), not random per request: it is unguessable without the key but identical prompts stay identical, which the Redis cache needs.
- **Checkpoints**: thread = the conversation's LangGraph thread, `durability="exit"` (one write per turn), a complete fresh state per turn with no reducers (nothing bleeds between turns; tested), and only references to evidence are checkpointed, never chunk text. PostgreSQL `messages` are the history; only messages of COMPLETED turns become model context (`recent_exchanges`).
- **Chat service** (`services/chat_service.py`, ADR-023 semantics): per-user chat rate limit (fails closed like other limits), then `begin()` (idempotent, 409 while busy) BEFORE any stream opens; the pipeline runs in its own task with a lease ticker (renewal every min(10, lease/3) s; losing the lease cancels the work); the turn is complete only after the validated answer is committed; persistence failure -> `PERSISTENCE_FAILED`, no text delivered, no cache write; client disconnect -> cancelled turn, user message kept, conversation freed; replay of a completed key returns the stored answer without a model call; replay of a failed/cancelled key -> 409 `TURN_FAILED`.
- **SSE** (`schemas/chat_stream.py`): `start`, `status*` (retrieving, generating, repairing, verifying, saving), `token*`, `citation*`, `complete` | `error`. Decision (also proposed by the plan and stricter than the spec asks): `token` events carry the already VALIDATED and already SAVED answer in ~32-character slices, after the commit. The cost is perceived latency (status events and 15 s keep-alive comments cover it); the benefit is that nothing unvalidated or unsaved is ever displayed and that replays produce the same events. Provisional streaming with retraction was rejected.
- **Findings from the tests:** a short quote/one-word "quote" proved nothing (quotes need >= 12 characters and 2 words); excerpt search must prefer a single sentence over a pair; question words had to be non-content words for routing; the answer cache is only useful for a repeated question in a conversation WITHOUT history (history is part of the prompt), so hit rates in multi-turn chat will be low: hits come mainly from repeated questions in new conversations (honest limit; measured in the evaluation when a key is available).
- Tests: 46 contract/verifier, 52 routing/prompt, 36 provider, 24 cache, 36 agent-graph (real PostgreSQL/Redis/Qdrant), 28 chat API incl. a real-socket disconnect and lease renewal, 1 end-to-end G6 scenario with the real Celery worker; 19 mutants (see log).

## ADR-027 (2026-11-11): Free hosted model provider and Redis LLM cache
- One OpenAI-compatible client (`llm/openai_compat.py`) covers Gemini (`https://generativelanguage.googleapis.com/v1beta/openai/`), OpenRouter (`https://openrouter.ai/api/v1`, `:free` models), Hugging Face Inference Providers (`https://router.huggingface.co/v1`) and Groq (`https://api.groq.com/openai/v1`); switching provider is `LLM_BASE_URL` / `LLM_MODEL` / `LLM_API_KEY` (+ `LLM_FALLBACK_MODELS`, `LLM_EXTRA_HEADERS`, `LLM_JSON_MODE`). Counters (`hit|miss|bypass|error`) are in Redis and the response metadata. The test suite blanks `LLM_*` so it can never reach a hosted model, even if `.env` has a key.

## ADR-029 (2026-11-11): Free-tier quota guard and `.env` model configuration
- Problem observed live: a free model hit its daily cap after 22 requests and every later request became a 429 (KI-035). Decision: count requests in Redis per model per provider day and per minute BEFORE calling the provider (`QuotaGuard`), refuse locally, let the fallback chain use the next model, and report an accurate `Retry-After`. Refused attempts cost no quota (counters are given back), concurrent requests cannot exceed the budget (atomic increments, tested with 40 parallel reservations), Redis problems fail open, an unknown timezone falls back to UTC.
- A per-user daily chat limit (`RL_CHAT_DAILY_LIMIT`) keeps one user from consuming the shared quota; the generation evaluation uses the same counters and refuses to run when the remaining budget is smaller than the run needs.
- The API key and all model settings are in the gitignored `.env` (never in code, logs, memory notes or git; `SecretStr`), and the test suite blanks `LLM_*`.
- Defaults in code are 0 = unlimited so the guard never surprises a self-hosted endpoint; the `.env` of this project sets 150/day, 10/min, 60 turns/user/day (calibration in docs/DEPLOYMENT.md, explicitly a conservative guess).


## ADR-030 (2026-11-12): Observability with OpenTelemetry, privacy by construction; evaluation reports
- Vendor-neutral OTLP/HTTP export, OFF unless `OTEL_ENABLED` and an endpoint are set (works with Phoenix, Langfuse's OTLP endpoint or a collector; only the OTLP path is verified, KI-037). One setup function for the API and the Celery worker processes. Tests install an in-memory exporter, so the whole suite runs with tracing active and asserts on real spans.
- Privacy is enforced where attributes are created, not by hoping call sites are careful: `safe_attributes` drops deny-listed keys (prompt, answer, query, question, message, content, text, quote, filename, email, token, key, memory, body, ...), redacts secret/e-mail-looking values, truncates, drops non-scalars; failed spans record only the exception type; the user is a hash. Redis query sanitizing on, SQL parameters, HTTP headers and bodies are not recorded. A scan of every exported span after a full chat turn and an upload is a test.
- Cross-process correlation: the outbox row stores the W3C `traceparent` (SQLAlchemy `before_insert` listener), the dispatcher sends it as a Celery header, `task_span` continues the trace. `X-Trace-Id` response header, `app.request_id` span attribute, `trace_id`/`span_id` in every log line.
- Alternative rejected: Langfuse/Phoenix SDKs in the app (vendor lock-in, extra dependencies, prompts captured by default). Prompt/answer content is deliberately NOT traced; debugging content is done from the database, where it is access-controlled.
- Evaluation: reproducible commands and committed reports (docs/EVALUATION.md); hand-labelled datasets are versioned (`routing_v1`); agent behaviour under failure is evaluated through the production graph with a scripted model (real PostgreSQL/Redis/Qdrant), and real-model runs respect the daily quota.

## ADR-031 (2026-11-12): Streamlit frontend that talks only to the API; feedback endpoint
- `frontend/` is a thin Streamlit app: `api.py` (httpx client: bearer tokens, one refresh on 401, typed errors, SSE stream), `errors.py` (wording by kind), `format.py` (pure helpers), `state.py`, `views/*` (auth, chat, documents, memory, account), `app.py` (sidebar navigation with a radio, not `st.navigation`, so `AppTest` can drive it). No imports from `backend/app`, no database or model access: the UI cannot bypass an authorization check because it holds no data access of its own.

Found by the UI tests, which first assumed same-key retry for everything.

Only the owner's assistant messages in live conversations can be rated; anything else is the same 404 (no id probing). Rate limit `RL_FEEDBACK_LIMIT` (120/h default).

## ADR-032 (2026-11-12): Dependency outages are 503/504, defensive response headers, test categories
- Found by the new outage tests: with PostgreSQL unreachable an exception escaped the request (a 500 on a real server). `core/dependency_errors.py` now maps connection-class failures (refused/reset, SQLAlchemy operational/interface/pool-timeout errors, Redis connection/busy errors, qdrant-client transport errors) to `SERVICE_UNAVAILABLE` 503 and timeouts to `UPSTREAM_TIMEOUT` 504, both with `Retry-After: 5`, the request id, no technical detail in the body (the detail is logged). Programming errors still take the 500 path. Liveness never depends on a dependency; readiness reports which one is down.
- Rate limiting still FAILS CLOSED when Redis is down (login and chat become 503, not unlimited); the LLM cache still fails OPEN (a cache problem never blocks an answer).
- `SecurityHeadersMiddleware`: `X-Content-Type-Options: nosniff`, `Referrer-Policy: no-referrer`, `X-Frame-Options: DENY`, `Cache-Control: no-store` (never overriding an endpoint's own value, e.g. the SSE `no-cache`), `Content-Security-Policy: default-src 'none'; frame-ancestors 'none'` (not on the development-only `/docs`), `Strict-Transport-Security` only when `APP_ENV=prod` (TLS terminates in front). CORS stays off unless `CORS_ORIGINS` lists exact origins.
- Test categories are markers assigned by file in one table (`backend/tests/conftest.py`) so one command per category exists (`scripts/test.ps1`); `pyright` strict now also covers `evaluation/` and `load_testing/` (56 existing errors fixed, no new suppressions beyond rule-named narrow ones for untyped third-party calls).

## ADR-033 (2026-11-13): Publication readiness, running the real stack, and what it found
- **Repository hygiene.** `.gitignore` covers secrets, caches, runtime data, `private/` (personal notes) and the author's local tooling (`.claude/`, `CLAUDE.md`: untracked but kept on disk); personal absolute paths were removed from tracked files; `.gitattributes` marks binaries (a PDF got corrupted by line-ending conversion otherwise); `examples/` holds fictional sample documents with checkable questions; `README.md` and `docs/LOCAL_SETUP.md` explain setup and use.
- **One-command local run.** `scripts/init_env.py` writes a `.env` with random secrets (never overwrites); `scripts/stack.py` migrates and starts API, worker, beat and UI and waits for health. On Windows children are started with `CREATE_NO_WINDOW | CREATE_NEW_PROCESS_GROUP` (with `DETACHED_PROCESS` they died with STATUS_CONTROL_C_EXIT when the launcher ended).
- **Windows event loop.** Running the actual server (not the tests) showed that uvicorn 0.54 creates a ProactorEventLoop on Windows whatever the loop policy says, so psycopg async (LangGraph checkpoints) failed and every chat turn timed out. `app.chat.checkpointer.selector_event_loop` is passed with `--loop`; regression tests prove the factory is loadable by uvicorn and usable by psycopg, and that psycopg rejects the Proactor loop.
- **Checkpointer.** First use is time-bounded (`CHECKPOINT_INIT_TIMEOUT_S`), logged by step and retried on the next request (a held setup advisory lock could stall the first turn once); old checkpoints are pruned after each turn (`keep_latest`), because every turn starts from a fresh state and the history lives in `messages`.
- **Observability you can use without a vendor.** `OTEL_TRACES_FILE` appends one JSON line per span; `scripts/trace_viewer.py` prints trees; OTLP export verified against Arize Phoenix 21 with real traffic (upload crossing into the worker, a chat turn). Known gap: SQLAlchemy 2.1 is not yet supported by the OTel instrumentation (KI-047).
- **Real browser.** `scripts/browser_tour.py` (Playwright, throw-away environment) found UI problems that AppTest cannot: polling that never started after the first upload, an upload notice wiped by a re-run. Both fixed; the AppTest suites remain the regression net.
- **Interface completeness.** Feedback is returned with the message list; MFA setup (QR via `segno`), e-mail verification, password reset and account deletion screens exist; a client bug was found by the new tests (a non-token 401, such as a wrong MFA code, signed the user out).

## ADR-035 (2026-11-13): Own database spans, checkpointer warm-up, structural event-loop test
- Database spans (KI-047): the OpenTelemetry SQLAlchemy instrumentor refuses SQLAlchemy 2.1, so `instrument_engine` (in `app/core/telemetry.py`) listens to the engine events `before_cursor_execute` / `after_cursor_execute` / `handle_error` on the async and the sync engine. A span is `db SELECT|INSERT|UPDATE|DELETE|OTHER` with `db.system`, `db.operation`, `db.rows`; it never carries the statement or its parameters (privacy rule of ADR-030), only starts below an existing trace, and an error records the exception type only. The unused library dependency was removed. Rejected: pinning SQLAlchemy < 2.1 (an older major for a tracing convenience) and recording statements with parameter masking (a masker is a bet that no user content ever reaches the text).
- Checkpointer warm-up (KI-048): the lifespan starts `CheckpointerProvider.warm_up()` as a background task. It never blocks or fails start-up; the lazy, time-bounded path in `get()` stays as the fallback, so a failed warm-up costs nothing but a log line. The root cause of the one observed stall is still unproven.
- Event-loop policy (KI-027): pytest-asyncio 1.4 has a supported `pytest_asyncio_loop_factories` hook, so `use_selector_loop()` (the deprecated `asyncio.set_event_loop_policy`) was deleted. The hook only parametrizes async tests; a sync test that requests an async fixture (our autouse `_clean_state`) got a different parameter and pytest tore down the session-scoped `infra` between the two kinds of tests (all `test_frontend_api` tests errored when they followed an async test), so `conftest.py` also parametrizes sync tests with the same factory (hidden id). `LiveBackend` uses `asyncio.run(..., loop_factory=selector_event_loop)`; a test asserts the tests run on a selector loop and that no code calls `set_event_loop_policy`.
- Event-loop test (KI-045): the property "nothing CPU-heavy runs on the event loop" is asserted by recording the thread of every Argon2 operation and PDF inspection (deterministic); wall-clock lag is only a loose secondary signal.

## ADR-036 (2026-11-13): Retrieval cache per user, question and knowledge-base version (KI-031)
- Cached: only the final ranking (chunk ids + rank/score numbers + candidate counts), in Redis under `retr:v1:u:<hashed user>:<sha256>`, TTL `RETRIEVAL_CACHE_TTL_S` (600 s), at most `RETRIEVAL_CACHE_MAX_BYTES`. The digest covers the NFKC/casefolded/whitespace-collapsed query, mode, top-k, the settings that change a ranking (models, depths, RRF k, rerank candidates and length, query prefix) and the knowledge-base fingerprint: a hash of the (document id, version) pairs the caller may read, which `DocumentRepository.readable` already computes for the Qdrant filter. A new document, a new version, a deletion or another scope changes the key, so nothing stale is served and no explicit invalidation exists to get wrong.
- A hit never trusts the cache for content: chunk payloads are reloaded from Qdrant by id (`scroll` with the same user and document filter plus the ids). If any cached chunk is gone the entry is stale and a full search runs; `RetrievalService` still re-verifies every chunk against PostgreSQL afterwards, as for a normal search. The citation verifier is unchanged.
- Fail-open with a 250 ms Redis timeout; degraded (a leg or the reranker failed) and empty results are never stored; entries are removed with the account (`purge_user_retrieval_cache_sync`, part of account purge). Observable: span attribute `retrieval.cache` (hit/miss/stale), counter `retrieval.cache`, `timings_ms.cache` in the search response.
- Rejected: caching chunk text (copies document content into Redis), caching per document (needs invalidation hooks in the worker), a longer TTL (the fingerprint already makes staleness impossible, the TTL only bounds memory).

## ADR-037 (2026-11-13): Optional model-based memory extraction (KI-026)
- `LlmMemoryExtractor` (`app/memory/llm_extract.py`) implements the existing `MemoryExtractor` protocol; `MEMORY_LLM_EXTRACTION` (default `false`) selects it through `build_extractor`, and only when a model is configured. Off by default because it spends one model call per consolidated conversation (free quotas, KI-035/036).
- One call per consolidation, `temperature 0`, JSON schema `{"facts": [{"fact", "kind": semantic|episodic, "importance": 1-5}]}` (strict: extra keys, unknown kinds, out-of-range importance and too-short facts are rejected), parsed by the agent's `parse_model_json` (no repair loop: a bad answer is not worth a second call). Only the user's own messages are sent, neutralised (`<` escaped) inside a nonce-tagged data block that the system message says is never to be obeyed; assistant text is not sent because it can quote the user's documents. At most 12,000 characters / 8 facts.
- The same gates as rule-based facts: sensitivity filter, 500-character limit and de-duplication in the extractor, and again in the pipeline (`_accept`, consent, per-user cap, content-hash de-duplication, retention). The pipeline does not know where a candidate came from, so there is no second, weaker path into the memory store.
- Counted by the quota guard (the call goes through `OpenAICompatibleModel`); consent is checked BEFORE extraction (no consent, no call, nothing leaves the server).
- Any failure (not configured, quota, timeout, provider error, invalid JSON) returns the rule-based result, so consolidation never fails or retries because of the model. A valid empty list is the model's judgement and stands.
- It runs in the synchronous Celery task through `asyncio.run` with its own HTTP and Redis clients (closed after the call), because the shared async clients belong to the API's loop.
- Rejected: summaries and a rewrite of old memories (a summary of a conversation that quotes documents is the highest-risk memory kind and is not needed yet); sending assistant turns for context (leaks document text to the provider and to memory).

## ADR-038 (2026-11-13): Re-ranking time: measured knobs, adaptive skip, warm-up (KI-023)
- Measured with `evaluation/retrieval/rerank_bench.py` (quality replayed on the production candidates for 36 synthetic + 28 real-document questions) and `evaluation/retrieval/rerank_threads.py` (interleaved latency, because sequential measurement drifted on the laptop and gave contradictory numbers). Reports: `evaluation/reports/rerank_bench.md`, `rerank_threads.md`.
- Kept: model `BAAI/bge-reranker-v2-m3-int8` (jina-v2-base-multilingual and MiniLM-L12 lose quality on at least one dataset); `RERANK_MAX_CHARS=2000` (1200/800 cut the answer-bearing sentence: synthetic hit@1 34/36 -> 12/36); 5 candidates; ONNX threads at the library default (`RERANK_THREADS=0`; pinning 2/4/8 threads was not faster: p50 5.3/4.1/4.4 s vs 4.1 s default for five 2000-character passages). Rule: `INFERENCE_THREADS x RERANK_THREADS <= logical cores` when set.
- Added: adaptive skip (`app/retrieval/skip.py`): the cross-encoder is not called when the best fused chunk is rank 1 in both dense and sparse lists and its RRF score leads the runner-up by `RERANK_SKIP_MARGIN` (relative). Default 0.1: no quality change on either dataset, 6 of 64 questions skip re-ranking. Recorded as `rerank_skipped` on the result and the span; part of the retrieval-cache key. Honest expectation: a modest average saving (~10% of questions save the full re-rank time); the large levers remain a GPU or `RERANK_ENABLED=false` (10 ms hybrid) when the quality trade-off is acceptable.
- Added: models are warmed at API start-up for local runs (`scripts/stack.py` and the generated `.env` set `WARM_MODELS_ON_STARTUP=true`), so the first question does not pay the model load.

## ADR-040: Terminate Windows sandbox work through its process handle
- Date: 2026-11-14. Actual unit verification reproduced a 120-second wait for a 2-second timeout.
- The unchecked external taskkill call can fail under restricted process-query permissions. Its
  failure was ignored and communicate()/wait() waited for the hostile child to exit naturally.
- Windows sandbox jobs limit ActiveProcessLimit to 1, so Popen.kill/TerminateProcess on the retained
  child handle terminates the entire allowed workload without depending on taskkill. Keep job-object
  resource limits and the POSIX process-group termination path. Existing timeout/memory/crash/recycle
  tests verify the fix (33 sandbox tests passed). This does not verify Linux container limits.
